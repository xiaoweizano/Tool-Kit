## Problem Statement

开发者日常有大量重复的「苦力活」:拼批量 SQL、解析 JSON、生成主键、时间戳互转、
md/Word 互转、SQL 占位符替换、正则生成、查 Linux 命令、Excel/md 互转、生成测试数据。
这些散落在编辑器/终端/在线小工具里,没有一个统一、有质感、离线可用的地方能把它们
一次做完。用户想要一个**一套代码、先在线过渡、后桌面可用(Windows/Mac)**的工具箱,
并持续扩展。

## What Makes This Cool

- **本地优先、桌面是本体**:几乎所有工具纯前端本地运算,服务器到期后桌面版 100% 完整
  可用,零降级。在线版只是「服务器到期前」的过渡形态。
- **一处用尽开发苦力活**:拼 SQL、转格式、生成 ID……一屏完成,粘进就出结果。
- **格式精确还原是硬承诺**:md↔Word、Excel↔md 的表格/标题/图片/列表还原比例要求高,
  UI 也因此是「展示→点一下→精确结果」的直接交互。
- **可扩展是设计原则**:加一个工具 = 加一个 `src/tools/xxx/` 目录 + 注册一行,桌面壳和
  在线版同时生效,为未来补充工具铺好路。

## Constraints

1. **核心承诺**:服务器到期后,桌面版(Win/Mac)必须能独立、完整可用。这要求几乎所有
   工具必须纯前端本地运算,不依赖后端服务。
2. 在线版是过渡(服务器快到期),桌面版是主线。
3. 未来可能需要后端(同步、AI),但这是可选增强,不能锁死或破坏本地优先承诺。
4. 中文 UI。
5. 需要「酷炫、现代化」的设计。

## Premises

- P1 — 工具扩展 = `src/tools/` 目录 + 注册表注册。加一个工具 = 加一个目录 + 在注册表
  登记一行,桌面壳和在线版同时生效,无需改壳。
- P2 — 本地优先 + 网络增强。所有非联网工具纯前端本地运算;Linux 命令大全 = 本地库兜底
  + 联网搜索增强;未来的同步/AI 是可选的网络增强层,**本地存储(默认 localStorage)永远是主库**,全流程保持在浏览器/Electron 渲染进程
  内,不依赖后端服务。
- P3 — 预留「数据源接口」。每个工具的数据读写通过抽象接口,未来接同步/AI 时把工具从
  async 层对接即可,不锁死纯前端现状。
- P4 — 技术基座:React + TypeScript + Vite + Electron(纯 JS,零 Rust 门槛,最速出桌面);
  构建工具用 Vite;md 用 turndown/marked、Excel 用 exceljs/xlsx、SQL 格式化自研等,具体
  库列于下,可后续微调。

## Approaches Considered

### Approach A: 一套 Web 代码 + Electron 桌面壳(选定)
- Summary: 单一前端仓库(src/tools/ 所有工具),构建出在线静态版;同一套代码用
  Electron 壳包装成 Win/Mac 桌面应用。本地优先,后端是可选增强。
- Effort: M(壳配置有一次性成本,但纯 JS 无编译坑)
- Risk: Low
- Pros:
  - 一套代码双输出,工具逻辑绝对一致,md/Excel 转换精度不会「网页/桌面不一致」。
  - 全项目一种语言(TS/JS),团队最易上手、AI 生成最顺。
  - 纯本地运算,天然满足「服务器到期桌面完整可用」。
  - 可扩展性最好:加目录 + 注册一行,双壳同步生效。
- Cons:
  - Electron 包大(100MB+)、内存占用高(自带 Chromium)。
  - 拿不到深度系统能力,但本产品工具用不到。
- Reuses: 单仓库复用 Vite 构建;turndown/marked/exceljs 等 JS 生态库。

### Approach B: 原生桌面(Flutter/Swift)+ 独立 Web 版(两套代码)
- Summary: 桌面用原生语言,在线版另用 Web 技术写一套。
- Effort: XL(两套独立代码,双份维护)
- Risk: Med(两套实现导致格式精度可能不一致)
- Pros:
  - 桌面 UI 最流畅、系统集成最好。
  - 不依赖系统 WebView。
- Cons:
  - 工具逻辑写两遍、修两遍 bug、验证两遍精度——你反复强调的「格式精确还原」会因两套
    实现而不一致,这是致命伤。
  - 双份维护成本,加一个工具要两遍。
  - 你这十个工具全是纯字符串/格式处理,原生 UI 的流畅优势根本体现不出来。
- Reuses: 无(两套都要重新实现)。

## Recommended Approach

**Approach A: 一套 Web 代码 + Electron 桌面壳,本地优先。**

理由,严格对应已确认的原则:
1. 主线是桌面、先在线过渡——只有一套代码能「在线→桌面」平滑迁移、零返工,两者本就是
   同一份前端。
2. 强调格式精确——A 保证网页和桌面看到同一份转换逻辑,永远不会一个精确一个还原得差。
3. 可扩展——加目录 + 注册一行,双壳同步生效。
4. 离线能力——纯本地运算,天然契合「服务器到期照样用」。
5. 成本最低——一个人、一种语言,一条线;Electron 纯 JS 零 Rust 门槛,最速出桌面。

## Technical Stack (锁定)

| 层 | 选型 |
|---|---|
| 前端框架 | React + TypeScript |
| 构建工具 | Vite |
| 桌面壳 | Electron(纯 JS,零 Rust) |
| 在线版 | 同一套代码,`vite build` 静态产物,任意静态托管(在线版仅过渡用) |
| 本地存储 | 默认 localStorage(满足当前无状态工具;若未来历史/收藏变重再引入 sql.js WASM 或 Electron main 进程 SQLite,需显式声明并兼容纯静态构建)— 见 reviewer 修正 |
| 后端 | 本地优先 + 网络增强;同步/AI 为可选增强层,不破坏本地优先承诺 |
| UI | 中文;Tailwind CSS + 组件库(shadcn/ui 或 daisyUI)+ 动效(Framer Motion) 打磨现代化质感 |
| 状态管理 | Zustand / Pinia(React 用 Zustand) |

## Tool Registry 扩展架构

```
src/
├── tools/
│   ├── register.ts        ← 工具注册表(声明 id / 名称 / 图标 / 路由 / 组件)
│   ├── sql-builder/       ← 工具1:租户 SQL 组装
│   ├── json-parser/       ← 工具2:JSON 解析/校验/格式化
│   ├── id-generator/      ← 工具3:主键 ID 生成
│   ├── date-converter/    ← 工具4:时间戳↔日期格式互转
│   ├── md-word/           ← 工具5:md↔Word 转换(高保真还原)
│   ├── sql-placeholder/   ← 工具6:SQL 占位符替换 + 格式化
│   ├── regex-generator/   ← 工具7:正则生成 + 常用列表 + 测试
│   ├── linux-manual/      ← 工具8:Linux 命令大全(本地库 + 联网增强)
│   ├── excel-md/          ← 工具9:Excel↔md 表格互转
│   └── testdata-gen/      ← 工具10:测试数据生成(表结构 → insert)
├── core/                  ← 通用:复制/历史/主题/数据源接口
├── data-source/           ← P3:抽象数据源接口(local/SQLite 实现 + 未来 async/云端)
└── app/                   ← 布局/导航/主题
```

**加一个新工具 = 创建 `src/tools/xxx/` 目录 + 在 `register.ts` 登记一行(名称/图标/
路由/组件)。桌面壳和在线版自动同时出现,无需改壳或改布局。**

## Data-Source Interface(P3 预留)

每个工具的数据读写不走直接 DOM/localStorage 直写,而是通过 `data-source/` 抽象接口:
当前实现 = LocalStore(SQLite / localStorage),未来接同步/AI 时新增一个 Async/Cloud 实现,
工具的调用点不变。这样后端是「可选增强」,不锁死纯前端现状。

## Implementation Order(实现顺序)

按「最快可用 + 高价值」排序,兼顾「先把纯本地版端起来」:

1. **脚手架 + Tool Registry + 布局骨架**:React/TS/Vite/Electron 跑通,导航 + 主题 + 空
   工具注册表——先把「扩展机制」立起来。
2. **JSON 解析工具**(工具2):最常用、实现简单,验证纯前端本地运算的闭环。
3. **时间戳↔日期转换**(工具4):实现简单、高频。
4. **SQL 占位符替换 + 格式化**(工具6):高频,实现中等。
5. **ID 生成器**(工具3):简单。
6. **租户 SQL 组装**(工具1):批量拼 insert,实现中等。
7. **md↔Word 转换**(工具5):保真要求高,单独深耕;先 md→表格/标题/列表,再 Word→md,
   图片/复杂表格逐项验证还原率。**这是精度承诺的重头。**
8. **Excel↔md 表格互转**(工具9):复用 md 转换的表格引擎。
9. **正则生成 + 常用列表 + 测试**(工具7):本地规则库 + 匹配测试;AI 增强留待后端可选层。
10. **测试数据生成**(工具10):表结构智能解析 + 生成 insert。
11. **Linux 命令大全**(工具8):本地命令库(覆盖基础 Linux 常用命令/选项/示例),联网搜索
    增强,支持「输入 h 提示相关命令」的搜索建议。
12. **桌面打包 + 在线部署**:Electron 产出 Win(.exe)/Mac(.dmg/.app);`vite build` 出静态
    在线版。服务器到期后在线下线,桌面主线顶上。

**AI / 同步(可选增强,第二阶段)**:接入 `data-source` 的 Async/Cloud 实现,给「正则从描
述生成」「Linux 命令语义搜索」「跨设备同步收藏/历史/模板」做增强。本地永远有兜底。

## Open Questions

- **md↔Word 引擎(已决定)**:软件采用 **pandoc**。纯前端库(html-docx 等)在复杂表格/嵌套
  列表/图片/Word 样式上保真受限,达不到「格式精确还原」硬承诺。设计采用**双层策略**:在线版用纯前端库(精度略低、可接受),
  **桌面版内嵌 pandoc 作为离线转换器**(约 150MB,由 Electron 以原生依赖方式打包携带)。这让
  「桌面版主线高保真、在线过渡版略低保真」显式成立,并在约束里如实重估包体积
  (Approach A 的「100MB+」修正为「额外 +~150MB 用于 pandoc」)。
  **待用户确认**此体积/依赖取舍。
- Linux 命令大全的本地库初始范围:覆盖多少条常用命令、多大体积,需权衡离线覆盖率与
  bundle 体积。
- 是否给工具加「历史记录 / 收藏模板」:会用到本地存储,也关系到 data-source 接口。

## Success Criteria

- 桌面版(Win + Mac):双击安装,能离线使用全部 10 个工具,无后端依赖也能跑通。
- 在线版:同源构建,服务器到期前可访问;到期后在线下线,桌面版无缝接管。
- md↔Word、Excel↔md:标题/表格/列表/图片的关键还原通过率 ≥ 某阈值(建议 95%,具体在
  Step 7/9 用样例集打分手测校准)。
- 加新工具:新增 `src/tools/xxx/` + 注册一行后,桌面+在线同时出现,零改壳。
- 本地优先:无网络时,除「Linux 联网搜索」「AI 增强」外的功能全可用,数据不丢失。

## Distribution Plan

- **桌面版(Win/Mac)**:Electron 打包,产 `.exe` / `.dmg`/`.app`。用 GitHub Actions 或手动
  Release 产出安装包,提供对应平台下载(CHANGELOG + 版本管理)。
- **在线版(过渡)**:`vite build` 静态产物,部署到 Vercel/Netlify/或自有服务器(当前
  Nginx/静态托管)。纯前端静态,无需后端。服务器到期后即下线。
- **CI/CD**:GitHub Actions 在 push/merge 时构建在线版 + 出桌面 Release。给 Release 加
  版本号(如 A-Tool-Kit v0.1.0),桌面端可内建「检查更新」。

## Dependencies

- 一次性块:初始化仓库 + 脚手架(React/TS/Vite/Electron 打通 + Tool Registry + 布局)。
- React 生态库按工具逐个引入;Electron 打包工具链(electron-builder)。
- 无外部服务依赖(纯本地优先);Linux 联网搜索为可选增强。

## CEO Review Findings (2026-08-24, HOLD SCOPE)

Mode: HOLD SCOPE — scope accepted, maximum rigor on edge cases, security, deployment.

### Scope decisions (all approved by user)
- **P1 (all 10 in v0.1)** — first release is the complete toolbox. **De-risked**: 桌面版是产品本体,在线版是「或有可无」的过渡;就算 v0.1 周期长到服务器到期,不影响桌面主线(桌面版可先于在线版发布)。
- **P2 (self-use first, future-open)** — 轻分发起步;仓库规范(LICENSE/README/通用打包配置)从第一天兼容未来。
- **P3-md (frontend libs in v0.1, pandoc to v0.2)** — 在线/桌面 v0.1 同源同精度;复杂表格/图片保真上限在 v0.1 如实标注,pandoc(桌面~150MB 离线增强)v0.2 提精度。
- **Distribution (full pipeline from start)** — CI/GitHub Actions/版本管理/检查更新 从 v0.1 就搭,不是后置。

### Reviewed edges hardened into the plan
1. **ToolDescriptor 接口契约(S1)** — 每个工具声明 input/output/error/capability(离线/联网/AI/异步)。加工具=实现接口+注册一行,扩展承诺真正成立;布局/壳按 capability 自动适配联网状态。
2. **每工具错误态** (S2) — 无静默失败。UI 三态 OK/ERROR/EMPTY;输入无效高亮定位、部分失败标注失败行、不支持的复杂结构明确提示。符合「零静默失败」首要指令。
3. **安全声明** (S3) — 本地优先=低攻击面。未来 AI 密钥:在线静态版无后端→不放任何密钥,AI 增强仅桌面、密钥进 OS keychain;在线版不转发用户内容(避 prompt 注入);解析(xlsx/docx/md)库引入时查 CVE/ReDoS;Electron 关 nodeIntegration、开 contextIsolation。
4. **golden-file 测试** (S6) — 每个转换工具建输入→断言输出的黄金样例;md↔Word/Excel↔md 建 10~20 覆盖标题/表格/嵌套列表/图片的样例文档库,作为「95% 保真」阈值的硬证据;补 JSON 边界/SQL 占位符不平衡/正则无效等错误态测试。工具=纯函数,天然可单测。
5. **核心交互:粘贴即出结果** (S11) — 有类型工具(JSON/时间戳/SQL/正则)粘贴后自动识别+即时转换+一键复制,无需点「转换」。是相对散落小工具的最强差异化。交互态 LOADING/EMPTY/ERROR/SUCCESS/PARTIAL全覆盖。

### NOT in scope (explicitly deferred)
- pandoc 原生高保真转换 → v0.2(桌面离线增强)。
- AI 增强(正则从描述生成/Linux 语义搜索)、跨设备同步 → 第二阶段,local-first 兜底。
